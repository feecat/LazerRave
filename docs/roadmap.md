# 开发路线图

本路线图定义 LazerRave 的阶段、依赖和交付门槛。桌面界面采用 C# / osu!lazer 源码组件，演奏由 C++ OpenLR2 执行，以同窗口嵌入为主要集成方式，并保留独立窗口与经典入口。后续功能沿用这一架构。服务器与实时状态通信尚未实现。

## 目标范围

首要目标平台为 Windows 10/11 x64。开发顺序为桌面应用、账号与内容服务、游戏桥接、多人游玩和质量完善，随后扩展现有后端的谱面与回放兼容性，并完成独立发行。每个阶段须保持现有本地游玩路径可用。

| 能力 | 首次交付阶段 | 完整化阶段 |
| --- | --- | --- |
| C# / osu!lazer 桌面应用、曲库及设置 | M1 | M5 |
| 高 DPI 与多语言界面 | M1 | M5、M7 |
| 段位课程与认证 | M1 前端与课程模型 | M3 游戏桥接、M6 规则及验证 |
| 账号、头像、签名 | M2 | M5 |
| 预设曲包目录与单曲下载 | M2 | M5 |
| 双人整局与输入事件回放 | M3 | M6 |
| 最多 16 人与同窗口实时排行 | M4 | M5 |
| 房主曲目打包、上传、分发 | M4 | M5 |
| 曲目响度分析与音频扩展 | M5 | M7 |
| BMS/BMSON 解析与回放验证 | M6 | 后续兼容扩展 |
| OpenLR2 演奏与 LR2 皮肤兼容 | 现有实现 | M5–M7 持续完善 |
| 独立发行包 | M7 交付门槛 | 沿用现有 C# 客户端与 C++ 后端 |
| Steam 身份接入 | S，可选 | 与发行渠道联动 |

## M0：可重现基线

状态：部分完成。

交付内容包括统一构建入口、明确的源码与资源布局、依赖版本记录、最小兼容样本、基线性能记录和根仓库 CI。

已具备 Windows x64 `RelWithDebInfo` 构建脚本、产物与运行目录划分、窗口尺寸工具、文档回归检查和根仓库 CI 配置。CI 尚需远端运行验证；可再分发样本、干净设备检查与完整性能测量仍待补齐。

验收条件：新开发环境可按文档获得一致构建结果；样本来源明确；配置和个人数据不进入发行包；失败可由日志与符号定位。

## M1：桌面应用

状态：部分完成。当前采用 [osu!lazer 桌面前端](development/client.md)，保留 OsuGame 主菜单、选曲及设置界面与 Mania 元数据规则集，接入 BMS 层级曲库、键型与难度筛选、预览、成绩读取及同窗口 OpenLR2 演奏。

依赖：M0 构建和运行基线。

交付内容：

- 维护单一 C# 桌面入口、共享设置和引擎桥接。
- 保留主菜单、选曲、设置及通用账号、多人与回放接口；已归档 osu!、Taiko、Catch、排位匹配、每日挑战和歌单界面。后续功能基于 BMS 与自有服务实现，不恢复 osu! 专用业务模块。
- 保留时间轴、撤销重做、音符及长音符工具、谱面属性与校验框架；后续接入 BMS 编辑模型、读写及保存校验。当前不提供 BMS 编辑入口。
- 自动保存新增演奏设置，明确保存失败和下一次会话生效的参数。演奏手感层（排列、血槽、速度、视觉项）与 mod 体系另见 [演奏模式与设置](development/gameplay-modes.md)。
- 完善后台扫描、增量索引、可取消操作和资源路径管理。
- 验证键盘、窗口、缩放和多语言，补齐亮色主题、段位课程与默认头像。
- 以原版界面为基础逐项适配，保持菜单、选曲、设置和游戏返回路径完整。
- 固定 BGA、帧时间和输入延迟的验收方法，比较独立与嵌入演奏。

验收条件：常用窗口及多显示器缩放下界面可用；扫描不阻塞界面；设置再次启动后保留；本地游玩、完整演奏与退出稳定；图片和视频 BGA 均通过本机验收。

旧前端与 framework 对比原型已归档，不再重复维护。客户端功能继续在 C# 中实现，演奏、解析及皮肤兼容继续在 OpenLR2 中扩展。服务端选型独立于客户端与引擎架构。

## M2：账号与内容目录

依赖：M1 应用服务边界。估算：4–6 人周。

交付内容：自有用户标识、密码认证、可撤销会话、头像与签名；首期采用邀请及管理恢复流程；建立公开曲目目录、单曲下载、断点恢复、完整性验证与缓存。新闻、更新日志和在线搜谱界面复用现有组件，逐步替换数据来源。

服务端采用 Axum、PostgreSQL 与对象存储。元数据和内容文件分别存储，公开目录与房间临时内容分别授权。Steam 身份作为可选绑定，不承担内部用户主键职责。

验收条件：离线功能不依赖登录；会话可撤销；用户资料更新权限明确；中断下载可恢复；损坏或未授权内容不能安装；目录条目具备来源与版本信息。

## M3：游戏桥接、双人原型与新回放

依赖：M1、M2。估算：6–10 人周。

交付内容：命名管道控制与状态接口、游戏能力握手、统一谱面和规则身份、准备与倒计时流程、双人整局、10 Hz 临时成绩快照，以及版本化输入事件回放。云端回放提供上传、授权下载、版本与完整性检查；排行榜区分实时临时分数和已确认的整局结果。

段位认证接入版本化课程、连续谱面演奏、血槽继承及本地记录。正式记录应包含课程与规则身份、排列设置和完成状态；在线验证及重算依赖 M6。

输入、音频与判定在本地完成。服务器管理房间和计划开局时间；网络延迟不直接修正判定窗口。初期可用伴随窗口验证排行，正式同窗口侧栏由 M4 交付。

验收条件：双机使用相同谱面、随机分支和规则完成整局；断线不阻塞本地游玩；同版本回放可重播；事件溢出、截断和身份不一致明确标记。旧 `.lr2rep` 保留兼容读取路径。

## M4：16 人房间与临时曲目分发

依赖：M3 稳定整局及 M2 内容服务。估算：4–7 人周。

交付内容：

- 房间容量扩展至 16 人，支持准备、候场、房主转移及断线重连。
- 实现左右可选、可隐藏的游戏内实时排行，处理 16 行显示与紧凑布局。
- 以完整单曲资源目录生成 ZIP，采用普通 Deflate 的最高常规等级 9，后台压缩并缓存。
- 实现分块上传、服务端校验、成员授权下载、客户端验证与原子安装。
- 对目录越界、大小写冲突、压缩包异常和资源缺失提供明确错误。

验收条件：16 协议会话及多台真机可完成整局；曲目和规则变更使准备状态失效；房主退出不导致进行中的比赛依赖房主连接；临时文件按引用及保留期清理；旧皮肤输入映射保持正确。

## M5：Beta 质量与音频扩展

依赖：M4。估算：6–10 人周。

交付内容：网络与进程故障恢复、限流与观测、恢复演练、完整 DPI 与多语言矩阵、回放结构校验，以及曲目响度分析和可关闭的音频处理。

响度参考采用选定谱面和随机分支的自动演奏混音，包含 BGM 与 keysound，整曲应用统一增益。EQ、压缩、限幅和响度补偿分别配置，附加 DSP 延迟纳入校准。

验收条件：100 在线规划负载通过容量测试；连续运行与恢复检查达标；音频处理不超延迟预算；实时排名明确为临时结果。M5 的结构校验不等同于服务器重算成绩。

## M6：谱面兼容与回放验证

依赖：M3 回放和版本模型、M5 样本体系。工作量在现有后端接口评估后确定。

交付内容：扩展 OpenLR2 现有解析与回放接口，完善 BMS 系列差异测试、BMSON 1.0.0 支持，以及可独立执行的回放验证任务。复用现有判定逻辑，先验证无界面重播与统计导出的可行性，再开放服务器重算。

谱面、资源包、展开时间线和规则版本分别标识。本地重播与后台验证使用匹配版本的 OpenLR2 后端；不支持的版本必须明确拒绝或选择已定义的兼容实现。后台任务的部署平台按原生依赖确定，不预设 Windows 游戏后端可以直接在 Linux 服务上运行。

验收条件：同一时间线、规则、种子和输入事件流重复执行得到相同判定与统计；约定 BMS/BMSON 样本通过；客户端成绩与重算结果可比较。确定性校验不作为真实人工输入的证明。

## M7：默认资源与独立发行

依赖：M5 质量基线及发行所选的兼容功能。默认资源整理可提前并行，工作量按素材与许可清单确定。

交付内容：打包现有 C# 客户端、OpenLR2 引擎、运行依赖和默认资源，完善首次运行、配置初始化与升级流程，并完成干净设备发行验收。

默认皮肤、字体、图片和音频须具备明确的发行条件。发行包使用嵌入演奏作为主要路径，同时保留独立窗口和经典模式；用户曲库、成绩及自定义资源不随程序更新覆盖。

验收条件：约定皮肤、谱面和回放矩阵通过；输入及音频延迟不超预算；默认资源来源明确；无需既有 LR2 安装即可启动、设置和游玩。发行形式可包含可执行文件、运行库及资源目录，无需限定为单文件程序。

## S：Steam 可选接入

依赖：M2 自有身份模型。估算：2–5 人周，独立于 M1–M7。

先按接入场景验证网页 OpenID 或原生应用票据。SteamID 映射至自有用户，不强制同步头像、签名或显示名。原生客户端接入需落实 AppID、发行条件及票据验证流程。

验收条件：绑定和登录验证在服务器完成；既有账号可恢复；Steam 不可用时离线功能保持可用。

## 依赖与工期

关键顺序为 M0 → M1 → M2 → M3 → M4 → M5。M6 兼容扩展与 M7 发行整理可在质量基线稳定后并行推进；默认资源整理可提前进行，Steam 接入按发行需求独立安排。

各阶段工作量须按现有后端接口、服务边界、兼容样本和资源清单重新评估。保留兼容性与性能的不确定性预算；阶段中的人周估算表示工作量，不构成日历交付承诺。

## 发布门槛

| 版本 | 必须满足的条件 |
| --- | --- |
| 基线版本 | 可重现构建、资源完整、现有游戏样本通过 |
| 多人 Alpha | 双机整局、断线不阻塞、同版本输入回放有效 |
| 多人 Beta | 16 会话与多真机验证、100 在线容量测试、回滚与恢复演练 |
| 兼容扩展版本 | 现有后端的皮肤、谱面与回放矩阵通过，实时性能无退化 |
| 独立发行版本 | 干净设备可用、默认资源完整、第三方依赖与素材发行条件明确 |

具体门槛见 [兼容性与质量标准](compatibility/quality.md)，服务容量假设见 [服务器容量](operations/server-capacity.md)。
