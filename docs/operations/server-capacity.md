# 服务器容量与运维规划

当前主机为 Ubuntu x86-64、1 vCPU、1 GiB 内存、32 GB NVMe。API、PostgreSQL 与 Caddy 单机部署，编译在开发设备完成；具体容器限制与操作步骤见 [云端部署](cloud-deployment.md)。配置上限不代表已验证容量，初期从单房间小规模测试开始。

## 容量约束

| 项目 | 当前约束或验证目标 |
| --- | --- |
| 房间 | 最多 16 人；验证双真机整局，再增加协议会话 |
| 实时通信 | 约 10 Hz 成绩快照，合并旧状态，限制慢连接积压 |
| 单 ZIP | 压缩最多 128 MiB，展开最多 512 MiB，10,000 个条目 |
| 内容配额 | 全站 8 GiB，其中房间临时内容预算 2 GiB |
| 内容校验 | 并发 1；预留上传暂存与校验空间 |
| 房间分享 | 校验完成后固定保留 2 小时；到期关闭下载并清理 |
| 未完成上传 | 闲置 1 小时进入清理流程 |

公开曲包与客户端已安装曲目独立于房间分享的生命周期。清理失败、重启补清理、数据库增长和内容卷剩余空间均需监控。回放文件配额在实际事件量与压缩率测量后确定。

## 带宽与性能预算

100 MB 曲目向另外 15 人分发一次，约产生 1.5 GB 出站流量；100 Mbps 聚合出口的理想耗时约 120 秒，未计入上传、压缩和协议开销。ZIP 最高常规压缩等级对已压缩音频的收益有限，带宽和出口额度应以实际曲包测量。

按每用户上行 512 B、每接收者下行 4 KiB、10 Hz 估算，100 在线原始载荷约为上行 4.1 Mbps、下行 32.8 Mbps，不含 TLS 和重传。100 在线仅作为后续负载测试目标，不作为当前主机承诺。

记录 API P95、房间广播延迟、快照年龄、连接数、上传队列、CPU、内存、磁盘和出口。连续高占用时先定位瓶颈，再调整内存、计算资源或内容出口；不提前固定未经实测的扩容规格。

## 备份与恢复

数据库与内容卷分别备份，副本放置于独立故障域。建议保留 7 份日备份和 4 份周备份，定期恢复演练；初始目标为 RPO 24 小时、RTO 4 小时，须经验证确认。

持久化 Caddy 证书和 ACME 账户数据，记录部署镜像、SQL 迁移版本及回退条件。密钥通过部署环境提供，数据库不开放公网端口。回放重算任务需要匹配版本的原生后端，其部署平台和资源预算独立评估。

## 验证顺序

1. 双真机验证认证、选曲、下载、准备、完整演奏及结果。
2. 16 个协议会话配合多台真机验证广播、慢连接和断线。
3. 测量曲包传输、并发房间及内容清理的资源峰值。
4. 进行连续运行，检查内存、磁盘、数据库和错误恢复。
5. 演练服务重启、磁盘不足、数据库恢复和版本回滚。

更大规模测试通过后再扩容。引入多实例前必须定义房间所有者路由和重连语义，增加缓存不能自动解决房间一致性。
