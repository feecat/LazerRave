# 技术栈与模块边界

本文区分当前实现与后续功能规划。前端为 C#，演奏为 C++ OpenLR2，两者通过 UTF-8 XML 请求及原生子窗口连接，曲库共享 OpenLR2 数据库。这一进程架构作为后续开发基础，以同窗口嵌入为主要集成方式，并保留独立窗口与经典入口。服务端与多人协议尚未实现。

当前 Windows 前端基于 C# / .NET 10 与经过裁剪的 osu!lazer 客户端 `OsuGame`，使用独立 BMS 数据适配和 OpenLR2 原生视口。旧前端原型已归档，具体范围见 [osu!lazer 桌面前端](../development/client.md)。

## 技术选型

| 层次 | 基准选择 | 职责与约束 |
| --- | --- | --- |
| 现有游戏 | C++23、DxLib、FMOD | 保持输入、音频、判定及旧皮肤运行能力 |
| 桌面界面 | C#、.NET 10、osu!lazer 2026.1005.0 | 复用上游真实选曲、字体、动画与设置组件；BMS 游戏仍由 OpenLR2 运行 |
| 应用服务 | C# 适配层与后台任务 | 隔离界面、桥接和内容服务，沿用现有客户端架构 |
| 异步与 HTTP 客户端 | .NET 异步任务与保留的客户端请求组件 | 后台任务、API 和内容下载 |
| 本地数据 | SQLite 与现有客户端存储 | 当前共享 OpenLR2 song.db，不修改成绩库结构；新内容索引按功能独立引入 |
| 多语言 | 上游本地化及客户端文本表 | UTF-8，新增主要控件覆盖中英日 |
| 游戏桥接 | 当前 UTF-8 XML 请求；后续 Windows 命名管道 | 现阶段直达演奏与曲库同步；实时控制和状态副本后续接入 |
| 服务端候选 | Rust、Tokio、Axum、tower-http | HTTPS API、WSS、认证、限流及观测；独立服务选型，不涉及客户端或游戏引擎重写 |
| 关系数据 | PostgreSQL、SQLx migration | 用户、内容元数据、对局和成绩 |
| 房间执行 | 单所有者任务、有界消息队列 | 顺序处理房间状态，避免并发状态漂移 |
| 文件存储 | S3 兼容对象存储 | 曲包与回放二进制、临时授权传输 |
| 内容归档 | ZIP，普通 Deflate level 9，SHA-256 | 后台打包、完整性验证及缓存 |
| 回放 | 版本化显式字段与输入事件 | 固定单位、字节序和规则身份 |
| 密码与会话 | Argon2id、随机可撤销会话 | 参数按容量验证，刷新凭据存摘要 |
| 部署 | Linux LTS、Caddy、Docker Compose | 初期单区域模块化单体 |
| 观测 | tracing、Prometheus 指标 | 请求、房间队列、任务和资源预算 |

当前 .NET SDK 固定为 10.0.401，设置由 Tomlyn 读写 TOML，谱面及皮肤编码由 C++ 统一处理。网络服务与游戏命名管道仍为目标设计；服务端工具链在独立服务建立时固定，不作为桌面客户端的构建依赖。依赖升级须独立验证。当前 C++ vcpkg 基线保持 `cd61e1e26a038e82d6550a3ebbe0fbbfe7da78e3`。

## 进程职责

| 进程或服务 | 主要职责 | 通信关系 |
| --- | --- | --- |
| C# 桌面应用 | 界面、曲库、本地配置与演奏生命周期；账号与房间待实现 | 当前 XML 启动协议及 Windows 子窗口；实时通信待接入 |
| C++ 游戏进程 | 谱面加载、实时输入、音频、判定与皮肤绘制 | 当前接收 XML 启动请求；实时控制、状态与回放事件接口待接入 |
| API 与房间服务 | 认证、内容授权、房间状态、计划开局和结果接收 | PostgreSQL、对象存储及任务队列 |
| 后台任务进程 | 包校验、元数据处理、后续回放重算 | 有界队列、对象存储；回放验证调用匹配版本的 OpenLR2 后端 |
| 对象存储 | 曲目和回放文件 | 客户端通过临时授权 HTTPS 传输 |

当前演奏已嵌入前端原生子窗口，经典独立窗口入口保留。嵌入式窗口须额外验证焦点、IME、DPI、全屏和 GPU 生命周期。多人 Beta 的同窗口排行需要游戏后端绘制适配，前端不会自动接管 DxLib 场景绘制。

## 并发与实时约束

游戏主线程消费经过验证的控制命令。IPC 工作线程通过有界队列与状态副本交换数据，不直接修改游戏内部对象。音频回调、输入采集和判定不得等待网络、数据库、压缩任务或下载锁。

界面任务支持取消和进度汇报。大量资源扫描、压缩、校验和解码采用有界后台并发，避免占用实时线程的 CPU 与磁盘预算。

现有 CustomIR 提供登录、成绩和排名相关接口，但尚不具备完整实时控制协议。不得以 C++ 标准库对象作为跨语言 ABI，也不得依赖注入或读取进程内存获取实时分数。

## 服务端数据与权限

关系数据按用户、认证身份、会话、资料、曲包、曲目、谱面、内容清单、上传会话、对局、参与者、成绩和回放元数据划分。文件内容存入对象存储，数据库保存身份、版本、摘要和权限信息。

房间状态初期驻留内存，由唯一所有者任务管理。完成的对局结果与必要记录持久化。服务重启后，进行中的比赛标记为中断；客户端可继续本地游玩，但未经服务器确认的结果不自动成为有效联机成绩。

公开目录与房间临时内容采用不同授权规则。对象键不能代替访问授权。头像、签名和自有显示名独立管理，不强制同步外部身份资料。

初期不引入 Redis、Kafka、Kubernetes 或分布式锁。扩展至多实例前，先定义房间所有者路由、重连及实例退出语义。

## 身份与离线能力

所有账号以自有 `user_id` 标识。密码使用 Argon2id 摘要，服务端可撤销会话；客户端凭据使用 Windows Credential Manager。认证参数、会话期限和限流预算在 M2 固定。

离线资料与本地游玩保持独立于在线认证。Steam 作为可选外部身份，网页 OpenID 和原生应用票据分别实现及验证。

## 现有架构的扩展顺序

1. 完善 C# 应用服务、设置及内容管理。
2. 扩展 C# 与 OpenLR2 之间的控制、状态和回放接口。
3. 接入账号、内容服务和多人房间，在现有游戏视口中实现实时排行。
4. 完善 OpenLR2 的谱面、皮肤及回放兼容，按性能预算接入音频扩展。
5. 整理默认资源、配置初始化与升级流程，完成独立发行验收。

各项扩展达到 [兼容性与性能门槛](../compatibility/quality.md) 后再默认启用。回放验证须先确认现有判定逻辑可以在受控环境下稳定重播；Windows 原生后端的任务节点与 Linux API 服务分别部署。
